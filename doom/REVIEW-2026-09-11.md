# Plan review, 2026-09-11

A pass over `plan/` looking for the class of defect that implementation has been turning up:
arithmetic that does not hold, claims stated as fact that were never checked, and
contradictions between documents. Every number below was recomputed rather than re-read.
Corrections are already applied; this file is the audit trail.

## Design gaps found (not arithmetic)

**Sprites would have been visible garbage.** 07's init enabled both backgrounds and sprites
in PPUMASK -- deliberately, because the read count was calibrated that way -- while the plan
elsewhere said sprite DMA was "not needed by Doom, reclaimed". Both are true and together
they are a bug: with sprites enabled and OAM left at its cold-boot zeros, 64 sprites sit at
the top-left corner and are drawn. Fixed by adding an init step that parks every OAM entry
at Y = `$EF` once, which keeps the fetch pattern the count depends on and costs nothing per
frame.

**The bus core had one table where the tutorial has two.** Found while testing, not reading:
`rp_system` keeps `m_ATR_W` (wanted) and `m_ATR_W_old` (last sent) and bulk data mode uploads
the *wanted* one. A single shadow made an upload send whatever the four-pokes-per-frame
trickle had synced so far -- wrong exactly when it matters, on the first frame after a scene
change. Fixed in `fcbus_core` (commit "Add the fcbus core, host backend, host shim and their
tests").

**A stopped link could never recover.** The host backend did not count reads taken while the
DMA was stopped, so a stopped frame reported a count of zero for ever. The real counter
advances regardless, and that advance is the whole recovery mechanism.

## Claims still unverified, and now labelled as such

- The 15490-versus-68-bytes-per-line contradiction (defect 3). **Gates M1 correctness**;
  needs P0-T9's trace. A cheap first hypothesis was added: CS1 may decode only
  `$0000`-`$0FFF`, using the PA12/PA13 lines the PIO leaves commented out, which would
  exclude every sprite fetch by construction.
- 4 MB flash, from another project's build settings, not a datasheet.
- `PICO_COM_WAIT` is 1279 cycles = 715 us, not the "roughly 1.3 ms" the vendor
  documentation states. Already flagged in 01; nothing depends on the difference except
  response-time headroom, which the shorter figure makes tighter.
- FamiStudio's command-line option names (its documentation was unreachable).

## What this says about the plan's reliability

The prose was sound; the numbers were not. Every defect above is in a figure, a table entry
or a cross-document claim, and eight of the ten were found by recomputing rather than by
reasoning. The lesson for the remaining documents is mechanical: any number that can be
derived should be derived in a test or a tool, not written down. `tools/gen_protocol.py`
already does this for the protocol constants -- which is why the APU cap was right in the
code and wrong in four documents.
