# RP2350 Doom UF2 build and picotool requirement

- Flashable RP2350 Doom firmware must be produced through pico-sdk's `picotool` path. Do not use `PICO_NO_PICOTOOL=1` or `PICO_NO_UF2=1`, and do not wrap `fcpico_doom.bin` directly into UF2 blocks. A manually wrapped image was flashed on 2026-09-25; the RP2350 returned to BOOTSEL and the NES displayed `PICO NOT FOUND`. Comparing that UF2 to picotool output from the identical firmware binary showed the manual image's final firmware UF2 payload was 168 bytes, while picotool emitted a 256-byte final payload with 88 bytes of padding. The picotool-built replacement was subsequently flashed: it showed USB descriptor failures and NES `PICO NOT FOUND`. Do not claim that the packaging correction fixed startup.
- Use project-local Arm GNU Toolchain 13.2 and `-DCMAKE_BUILD_TYPE=MinSizeRel -DFCPICO_BUILD_ENGINE=ON -DFCPICO_DIAGNOSTIC_ENGINE_DELAY=ON`. Native NESASM CE is pinned to commit `6fc41cda37b934aa29aa2639d0baa74424268e31`; set `NESASM_BIN` during build. Run `python3 doom/tools/flash_layout_check.py <build>/rp2040-doom/src/fcpico_doom.elf`.
- For an existing picotool 2.1.1 CMake install, pass `-Dpicotool_DIR=<install>/lib/cmake/picotool` to the Doom CMake configure. Confirm `fcpico_doom.uf2` is emitted by target `doom_tiny_fcpico`. Merge with `python3 doom/tools/whx2uf2.py doom/rp2040-doom/doom1.whx <output>.uf2 --firmware <build>/rp2040-doom/src/fcpico_doom.uf2`; WHX is at `0x10080000`. Run `picotool info -a <output>.uf2` and verify firmware/WHX payloads and SHA-256.
- If picotool is unavailable, look for an existing installation and `picotoolConfig.cmake` first. Otherwise fetch official `raspberrypi/picotool` tag `2.1.1`, configure and build it as a host tool, then point `picotool_DIR` at its installed CMake package. Example: `git clone --branch 2.1.1 --depth 1 https://github.com/raspberrypi/picotool.git /tmp/fcpico-picotool-source`; `cmake -S /tmp/fcpico-picotool-source -B /tmp/fcpico-picotool-build -G Ninja -DCMAKE_BUILD_TYPE=Release -DCMAKE_INSTALL_PREFIX=/tmp/fcpico-picotool-install -DPICO_SDK_PATH=/home/josh/.local/fcpico/pico-sdk -DCMAKE_POLICY_VERSION_MINIMUM=3.5`; `cmake --build /tmp/fcpico-picotool-build -j 4`; `cmake --install /tmp/fcpico-picotool-build`. Then use `-Dpicotool_DIR=/tmp/fcpico-picotool-install/lib/cmake/picotool`. The policy flag was needed with local newer CMake and bundled mbedTLS. libusb was absent, but file conversion still built.
- The older documented known-good configure command is in `doom/PROGRESS.md` under device verification (search `picotool_DIR`). A differing hash from a recorded candidate is a new build and needs hardware validation.
- Preserve `FCPICO_DIAGNOSTIC_ENGINE_DELAY=ON` when rebuilding the current hardware candidate. Earlier working images retained this option. It enables the 30-second countdown, bus statistics and raw PIO read counter; the two failed rebuilds accidentally omitted it. The user flashed the restored profile and confirms working Doom, much better contrast and working B input. Serial remains stable through 1829 heartbeats at count=15554, stops=1/resyncs=1, zero errors/timeouts and drops settled at 691. Conversion average/max at 480 frames is 38208/38251 us. Which part of the diagnostic profile is required has not been isolated; retain the whole profile. The restored candidate is `/tmp/fcpico_doom_shadow_detail_delay_whx.uf2`, SHA-256 `3d298001d93f028dd6a3e9f37287e8d77762704b0c1295485c8fd22275f88dbc`, 8158 blocks, firmware 287836 bytes. It differs from the original recorded HR-6 hash. See `doom/HARDWARE-LOG.md` (2026-09-25) for findings and pending serial capture.
- Check the root project's bundled `tutorial_project/bin/picotool.exe` before downloading another tool. It reports Windows picotool v2.3.0 and works through WSL Windows interop. In the agent sandbox, Windows interop failed with `UtilBindVsockAnyPort`; running the read-only/conversion command with approved escalation worked. The bundled file lacked its Linux executable bit; copying it to `/tmp/fcpico-project-picotool.exe` and chmodding that copy avoided modifying vendor files. Use `wslpath -w` to pass ELF/UF2 paths. Windows v2.3.0 and native v2.1.1 produced byte-identical firmware UF2s from the same restored ELF on 2026-09-25. Previous documented Doom builds used native v2.1.1; do not claim that the Windows executable was previously used for those builds without evidence.

- Durable milestone entry point: `doom/tools/build_shadow_detail.sh` (or `--bootstrap-tools` to build missing pinned native tools). Default artifacts live under ignored `.build/doom-shadow/artifacts/`; no dependence on `/tmp`. Supports `PICOTOOL_DIR`, `NESASM_BIN`, `PICO_SDK_PATH`, `ARM_TOOLCHAIN_PATH`, `BUILD_DIR`, `TOOLS_DIR`, `JOBS`. It forces the working diagnostic profile, requires GCC 13.2.1/SDK 2.1.1, runs the tutorial ROM MD5 and flash layout gates, uses SDK picotool UF2 output and merges WHX. A fresh script build reproduced the hardware-tested merged UF2 SHA-256 exactly on 2026-09-25. See `doom/plan/08-build.md` for usage and `doom/HARDWARE-LOG.md` for milestone evidence.
