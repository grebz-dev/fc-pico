# Host and simulation traps

- The host build uses `PICO_PLATFORM=host` with `doom/sim/host_shim/` for missing pico-sdk 2.1.1 multicore, alarm and assertion functions. The SDK's weak `get_core_num()` always returns 0; the shim overrides it with thread-local core identity. Its inter-core FIFO is two independent 8-entry blocking pthread queues.
- Host pico-sdk `hardware_sync` spin locks are dummy, single-threaded locks. Shared `pico_sync` semaphores across genuine pthreads may race, and `__wfe()` can busy-spin after the first event. The shim uses pthread synchronization for its own FIFO. Use `host_cancel_repeating_timer()` for shim timers; SDK `cancel_repeating_timer()` can panic on successful cancellation.
- `doom/sim/pioemu/` tests assemble the real `doom/fcbus/fcppu.pio`. With pioemu 0.88, IRQ set/wait/clear is not meaningfully emulated, so `fcppu_dir` has only an assembly check and bus turnaround needs higher-level simulation or hardware. pioemu FIFOs are four words, without hardware FIFO join. Adafruit's assembler needs preprocessing; `conftest.py` owns it.
- `doom/sim/ppubus/` models the sequence/count of console reads and NMI writes, not firmware byte offsets. It shares 2bpp bit packing with `fcpico.stream`, but `PpuBus.reference_buffer()` is required for `SimpleCart`/`reconstruct()`; a buffer from `fcpico.stream.encode_frame()` cannot be substituted byte-for-byte. `ppubus.py` documents the API and accounting.
- The test layers are complementary: host C/Python checks, pioemu, PPU-bus/cart models, Mesen2 scenarios, and physical console evidence. A passing emulator screenshot does not establish physical bus timing. Keep exact session evidence in `doom/PROGRESS.md` and `doom/HARDWARE-LOG.md`, not memory.
